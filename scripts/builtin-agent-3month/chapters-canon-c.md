### 技术要点
- 归因回答的是「**失败出在哪一层**」，而不是「这次失败了吗」——后者是评测集的事
- Agent 的失败至少分五层：**模型能力、提示与指令、工具与接口、外部数据、评估标准本身**
- 归因必须能区分**随机波动**与**真实退化**，否则会把噪声当回归
- 最常见也最容易被误判的一层是「评估标准本身有问题」：把评测集的缺陷当成模型缺陷

### 深入讲解

归因的价值在于**决定下一个动作**。同样一次失败，「模型选错了工具」要改提示或工具设计，「工具返回超时」要改超时与重试策略，「检索资料本身是过期的」要改数据源。没有归因，这些动作都变成猜。

可用的分层判据：

| 层 | 判据 | 复查方式 |
| --- | --- | --- |
| 模型能力 | 同一提示重复跑，失败率高于阈值且错误类型一致 | 换更强的模型试同一任务 |
| 提示与指令 | 换模型仍失败；人工按提示执行能做对 | 人工按字面执行提示 |
| 工具与接口 | 工具调用本身的失败率高，与任务难度无关 | 单独压测工具 |
| 外部数据 | 工具成功但返回内容与预期不符 | 直接检查数据源 |
| 评估标准 | 失败样本人工判定其实是正确的 | 人工复核评测集 |

这张表里最有用的是**第二行与第五行**。第二行用「人工按提示执行」来判定指令是否有歧义——这是把人当作模型来运行同一份提示，成本极低但极其有效。第五行则是防止「优化评测集而不是优化系统」这种自欺。

关于随机波动：单次失败不构成退化证据。可行做法是**每次评测重复多次并看分布**，同时把「同一提示重复执行的通过率变化」作为信号。如果通过率从 80% 降到 75%，在样本量只有 20 条时，这个差异大概率还在噪声范围内。

### 代码实例

```js
// 分层归因：先排除「评估标准」这一层，再逐层下探
function attribute(failure, context) {
  // 1. 评估标准：人工复核后其实是对的 → 修评测集，不要修系统
  if (context.humanReview?.verdict === 'actually_correct') {
    return { layer: 'evaluation', action: '修订评测集与判定规则' }
  }
  // 2. 工具层：工具自身失败率高，与任务无关
  if (context.toolStats.failureRateWithoutTask > 0.2) {
    return { layer: 'tool', action: '修工具的超时/重试/接口契约' }
  }
  // 3. 外部数据：工具成功，但内容与预期不符
  if (context.toolOk && context.dataMismatch) {
    return { layer: 'data', action: '修数据源或加数据新鲜度校验' }
  }
  // 4. 提示层：人工按同样提示能做完
  if (context.humanReplay?.success) {
    return { layer: 'prompt', action: '消解指令歧义，或补上缺失的约束' }
  }
  return { layer: 'model', action: '评估换模型或补更强的脚手架' }
}

// 降低噪声误判：重复执行看分布，而不是看单次结果
function isRegression(baseline, current, { repeats = 5, tolerance = 0.1 } = {}) {
  const delta = baseline.passRate - current.passRate
  const noise = Math.sqrt(baseline.passRate * (1 - baseline.passRate) / (baseline.n * repeats))
  return delta > Math.max(tolerance, 2 * noise)
}
```

### 常见误区与考点
- ❌ **把所有失败都归给模型能力**。这会导致频繁换模型，而问题常常在工具契约或数据源上。
- ⚠️ **考点**：为什么「人工按提示执行一遍」是很高价值的归因手段？——它把提示当作程序来运行，能直接暴露指令歧义，而歧义无法从模型输出反推。

### 技术要点
- 灰度要回答两个具体问题：**先放给谁**、**坏到什么程度必须回滚**——两者都要在发布前写下
- 回滚能力比发布流程更优先：**不可回滚的 Agent 不应该上线**
- 关键指标要包括**行为类指标**而不只是成功率：工具调用次数、人工介入率、单次成本
- SLO 要区分「用户可感知」与「内部效率」两类，前者是底线，后者是优化目标

### 深入讲解

Agent 的上线风险与普通服务有一个本质差别：**它的失败常常不是报错，而是看起来成功了**。接口返回 200、任务显示完成，但结果是错的。所以灰度阶段的判据不能只有错误率，必须包含**行为可观测指标**：

- **工具调用次数分布**：显著上升往往意味着循环退化或工具选择变差——这是最早能看到的信号。
- **人工介入率**：本来自动完成的动作开始需要审批，说明权限或置信度出现了变化。
- **单次任务成本与延迟**：它们的上升通常先于质量下降出现。
- **任务重试率与放弃率**：用户放弃比用户报错泄露更多信息。

灰度的人群选择也有讲究。对 Agent 而言，合理的顺序是：**内部用户 → 低风险任务类型 → 全量任务类型 → 全量用户**。注意第二个维度是**任务类型**而不是用户量：把「只读查询」先放开，比把 10% 的用户全量放开更安全，因为前者限定的是爆炸半径。

回滚的标准要可判定。模糊的「效果不好就回滚」等于没有标准。可用的写法是具体的阈值组合，例如「工具调用次数中位数上升超过 40%，或人工介入率超过 15%，任一持续 30 分钟即回滚」。这些阈值在发布前定，发布中不修改——否则每次异常都会被解释成「再观察一下」。

最后是 SLO 的分层。用户可感知的（响应时间、任务成功率、错误可见性）是底线，违反即回滚；内部效率的（单次成本、token 消耗、缓存命中率）是优化目标，违反触发排查但不一定回滚。混在一起会导致要么过度敏感、要么长期麻木。

### 代码实例

```js
// 发布前写死回滚条件：发布中不修改，避免「再观察一下」式的解释
const ROLLOUT = {
  stages: [
    { name: 'internal', scope: { users: 'internal' }, minHours: 24 },
    { name: 'readonly-tasks', scope: { tasks: ['read_query', 'search'] }, minHours: 24 },
    { name: 'all-tasks', scope: { users: 'internal', tasks: 'all' }, minHours: 48 },
    { name: 'public', scope: { users: 'all' }, minHours: 0 },
  ],
  // 任一条件持续 30 分钟即自动回滚
  rollbackIf: [
    { metric: 'tool_calls_p50', rule: 'increase_ratio', threshold: 0.4, windowMin: 30 },
    { metric: 'human_intervention_rate', rule: 'above', threshold: 0.15, windowMin: 30 },
    { metric: 'task_abandon_rate', rule: 'increase_ratio', threshold: 0.5, windowMin: 30 },
    { metric: 'p95_latency_ms', rule: 'above', threshold: 60_000, windowMin: 30 },
  ],
}

function shouldRollback(metrics, window) {
  return ROLLOUT.rollbackIf.find(rule => {
    const series = window.series(rule.metric, rule.windowMin)
    return series.length > 0 && series.every(v => compare(v, rule))
  })
}
```

### 常见误区与考点
- ❌ **只用错误率作为判据**。Agent 最危险的失败是「静默出错」——指标正常，结果是错的。
- ⚠️ **考点**：为什么灰度优先按「任务类型」而不是「用户比例」划分？——任务类型直接限定能力范围，也就是限定爆炸半径；用户比例只限定受影响的人数。

### 技术要点
- 协议决定**可替换性**：换模型、换工具、换供应商时，要改多少处代码
- 这一层的问题不是「怎么调用」，而是「**边界画在哪**」：适配层的位置决定迁移成本与能力上限
- 生态是协议的真实价值来源：有现成工具集的协议，比设计更优雅但无人实现的协议更有用
- 协议分支在个人探索里几乎不会出现——它属于「不看地图就不知道自己缺」的典型

### 深入讲解

这一支回答一个很实际的问题：**当你想换模型、换工具、或者引入第三方工具时，代价是多少。**它包含三个层次：

| 层次 | 回答的问题 | 对应节点 |
| --- | --- | --- |
| 调用形态 | 工具调用长什么样（结构化输出、错误表示） | 跨厂商互操作与适配层 |
| 资产管理 | 工具从哪来、什么版本、谁有权用 | 工具注册表与版本管理 |
| 选型代价 | 选了这个协议，将来迁移要改多少 | 协议选型与锁定成本 |

为什么这一支对自学者最难自发形成？因为**单模型、单工具集的原型阶段感受不到它的存在**。只有当你想比较两个模型的工具调用表现，或者想把一个手写的工具换成社区现成的实现时，协议问题才会以「要改一大片代码」的形式突然出现。而在那之前，没有任何信号提示你去研究它。

一个值得记住的判断：**适配层放在越靠内层，迁移成本越高，但能力利用越充分**。把适配放在最外层（模型输出先转成统一格式再进入主循环），迁移成本最低，代价是你只能用各家的公共子集；把各自特性往上透传，能力用得最足，但主循环会被厂商细节渗透。这是真实取舍，没有普适答案——但**必须是一个被有意识做出的选择**，而不是随代码长出来。

### 常见误区与考点
- ❌ **等到需要换模型时才考虑协议**。那时代码已经深度耦合，改造代价远高于设计时预留。
- ⚠️ **考点**：为什么说「有现成工具集的协议」比「设计更优雅的协议」更有价值？——协议的成本不在实现规范，而在生态积累；没有实现的协议等于要自己造全部配套。

<!-- node: canon_registry -->
### 技术要点
- 注册表是**工具身份与版本的唯一事实来源**：名称、版本、参数契约、权限要求都在这里定
- 工具会**改名、换参数、下线**，所以引用必须走 ID 而不是名称
- 版本升级要能**并存与灰度**：同一个工具的两个版本可能同时被不同任务使用
- 注册表必须**对模型可见的部分与对运维可见的部分分开**：模型只需要参数契约，不需要内部实现信息

### 深入讲解

注册表要解决的问题看起来很简单——「有哪些工具可用」——但它真正的价值在变化发生时才显现。工具是会长大的资产，典型变化有三类：

1. **改名**：为了更清晰的表达调整工具名。如果提示词或历史记录里硬编码了旧名字，改名就会静默失效（模型继续按旧名调用，然后被拒绝）。
2. **换参数**：新增必填参数、修改参数语义、收紧取值范围。这类变化最危险，因为它会让原本正确的调用变成错误调用。
3. **下线**：某个工具被替代。历史任务重放时会找不到它。

对应到设计上，三条要求：

- **引用走 ID**：内部用稳定 ID 标识工具，名称只是展示字段。这样改名不影响既有引用。
- **版本并存**：注册表支持同 ID 多版本共存，任务记录它使用的版本；新版本先按比例灰度，出现问题时按版本回滚，而不是回滚整个系统。
- **契约可校验**：参数契约能被程序读取并用于校验模型输出。这一点除了防错，还有一个附带好处——可以把契约自动转成给模型的工具定义，避免「文档与实现不一致」。

还有一个容易忽略的分层：**注册表对模型可见的部分应该最小化**。模型只需要知道名字、用途说明和参数契约；超时、重试策略、内部实现、负责人这些运维信息不应该进入上下文——既占额度，也是不必要的信息暴露。

### 代码实例

```js
// 注册表：稳定 ID + 多版本并存 + 契约可校验
const REGISTRY = {
  'tool.db_query': [
    { version: '1.0.0', status: 'deprecated', since: '2026-05-01',
      contract: { params: { sql: 'string' }, returns: 'rows' } },
    { version: '0.9.1', status: 'active',
      // 语义化参数，范围可校验；模型只看到这一段
      contract: { params: { query: 'string', limit: 'number<=1000' }, returns: 'rows' },
      // 运维信息不进上下文
      ops: { timeoutMs: 5000, retries: 1, owner: 'data-platform' } },
  ],
}

function resolve(toolId, pinnedVersion) {
  const versions = REGISTRY[toolId] || []
  const hit = pinnedVersion
    ? versions.find(v => v.version === pinnedVersion)
    : versions.find(v => v.status === 'active')
  if (!hit) throw new Error(`工具不可用: ${toolId}@${pinnedVersion || 'active'}`)
  return hit
}

// 模型可见的只有契约部分
function toModelSchema(toolId) {
  const { version, contract } = resolve(toolId)
  return { name: toolId, version, parameters: contract.params }
}
```

### 常见误区与考点
- ❌ **用工具名做唯一标识**。改名意味着所有历史引用与提示词同时失效，且失败是静默的。
- ⚠️ **考点**：为什么注册表要区分「对模型可见」与「对运维可见」？——前者影响推理质量与上下文成本，后者涉及内部实现，混在一起两头都不讨好。

### 技术要点
- 各厂商的**工具调用格式并不统一**：字段命名、参数编码、错误表示、并发调用支持程度都不同
- 适配层的位置是一个真实的架构决策：**越靠外迁移成本越低、能力利用越保守**
- 统一抽象应当只覆盖**公共子集**，厂商特性通过**可选扩展**暴露，而不是强行抹平
- 跨厂商的差异最容易被低估的是**流式与工具调用同时发生时的分帧行为**

### 深入讲解

把不同厂商的工具调用放在一起看，差异集中在四处：

| 维度 | 常见差异 | 对代码的影响 |
| --- | --- | --- |
| 工具定义 | 字段名与嵌套结构不同 | 序列化层要转 |
| 调用表示 | 独立字段 vs 文本内标记 | 解析层要分支 |
| 参数编码 | JSON 字符串 vs 原生对象 | 校验层要兼容两种情况 |
| 流式分帧 | 工具调用参数是否分片到达 | **增量解析器要重写** |

第四项是最容易在迁移时踩到的：有的实现把工具调用参数一次性给全，有的会分多次给出片段，需要增量拼接后再解析。如果解析器假设「一次给全」，在另一家模型上会得到半截 JSON 解析失败，而且失败表现为间歇性——只有参数较长时才出现。

适配的两种基本位置：

**外侧适配**（推荐起点）：主循环只认统一格式，厂商差异全部收敛在适配器里。迁移成本最低，代价是只能用各家能力的公共子集——例如某家支持在一次响应里并行多个工具调用，另一家不支持，那么外侧适配就只能退化成串行。

**内侧透传**：厂商特性向上暴露，主循环感知具体能力。能力用满，但主循环被厂商细节渗透，迁移时要改的地方多。

合理的做法是**外侧适配加可选扩展**：默认走公共子集，同时允许适配器向上报告「本厂商支持并行调用」这样的能力标记，主循环在检测到标记时启用优化路径。这样大部分代码与厂商无关，少部分关键路径可以按能力分支。

### 代码实例

```js
// 统一表示 + 能力标记，而不是强行抹平差异
const UnifiedToolCall = {
  id: 'call_1', name: 'db_query', args: { query: 'select 1' },
}

// 适配器：负责把所有厂商形态转成统一表示，并声明能力
const adapters = {
  plain: {
    capabilities: { parallelToolCalls: false, streamedArgs: false },
    parse: raw => raw.tool_calls?.map(c => ({
      id: c.id, name: c.function?.name, args: safeParse(c.function?.arguments),
    })) ?? [],
  },
  streamed: {
    capabilities: { parallelToolCalls: true, streamedArgs: true },
    // 增量拼接：参数可能分片到达，必须累积后再解析
    createCollector() {
      const buffer = new Map()
      return {
        push(delta) {
          const slot = buffer.get(delta.index) || { id: delta.id, name: '', argsText: '' }
          if (delta.name) slot.name += delta.name
          if (delta.argsText) slot.argsText += delta.argsText
          buffer.set(delta.index, slot)
        },
        finish() {
          return [...buffer.values()].map(s => ({ id: s.id, name: s.name, args: safeParse(s.argsText) }))
        },
      }
    },
  },
}

function safeParse(text) {
  try { return JSON.parse(text) } catch { return { __unparsed: text } }   // 显式失败，不猜
}
```

### 常见误区与考点
- ❌ **假设工具调用一定会一次给全**。分片到达时，解析器会周期性地拿到半截 JSON。
- ⚠️ **考点**：为什么统一抽象应该只覆盖公共子集？——把厂商特性强行抹平会隐藏能力差异，导致「换模型后任务变慢」这类难以定位的性能退化。

<!-- node: canon_lockin -->
### 技术要点
- 锁定成本要**算成可数的改动点**：「迁移要改多少处代码、多少条提示词、多少个工具定义」
- 锁定不只来自协议，也来自**提示词的模型特化**——为某个模型的怪癖专门写的补丁最难迁移
- 评估维度是三维的：**迁移成本、能力上限、生态成熟度**，三者通常不能同时最优
- 成本要**在选型时算清**，而不是在迁移时才发现

### 深入讲解

锁定常被理解成「用了某家的专有 API」。实践中更常见、也更隐蔽的锁定来源是**为特定模型的行为打的补丁**。举几个真实形态：

- 为了让某模型稳定输出 JSON，在提示词里写了针对性的格式化要求。
- 为了绕过某模型的工具调用怪癖，在解析器里加了特例分支。
- 为了让某模型的表达能力够用，把提示词写得非常长且高度结构化。

这些补丁在那个模型上工作良好，但它们**把模型特性写进了系统**。换模型时，它们不会报错，只会让效果变差——这是最难处理的迁移问题，因为没有明确的失败点。

算锁定成本可以用一个简单的三列表格：

| 资产 | 数量 | 迁移时是否要改 |
| --- | --- | --- |
| 工具定义与适配器 | 按工具数 | 若用了专有格式则要改 |
| 提示词中的模型特化补丁 | 按补丁数 | 基本都要重写 |
| 评估基线 | 一套即可 | 不必改，但**必须重跑** |

第三行是重点：**评估基线是跨模型迁移的关键资产**。有它，迁移才是一次可比较的实验；没有它，迁移就是「感觉快了/慢了」的印象判断。所以在选型阶段就应该先把评测集建起来——它的收益远不止迁移，这是评估板块与协议板块之间真正的依赖关系。

最后是三维取舍。生态成熟度最难通过自研弥补，所以**在能力上限可接受的前提下，优先选生态更成熟的协议**；而迁移成本则是可以通过架构（外侧适配层）主动降低的，属于「可以自己控制」的那一维。

### 代码实例

```js
// 选型打分：把三维量化，避免只盯着「能力强」这一维
function scoreOption(option, { weights = { migration: 0.4, capability: 0.3, ecosystem: 0.3 } } = {}) {
  // migration：改动点越少得分越高
  const migrationCost = option.changePoints.code * 1 + option.changePoints.prompts * 3
  const migration = 1 / (1 + migrationCost / 20)
  return {
    total: migration * weights.migration
      + option.capabilityScore * weights.capability
      + option.ecosystemScore * weights.ecosystem,
    detail: { migration, ...option.capabilityScore ? {} : {} },
  }
}

// 迁移前的必备前提：评估基线存在，否则迁移不可比较
function canMigrate(evalBaseline) {
  if (!evalBaseline || evalBaseline.cases < 20) {
    throw new Error('没有足够的评测基线，迁移结果无法比较。先建评测集。')
  }
  return true
}
```

注意提示词的权重是代码的 3 倍：**模型特化补丁的重写成本，通常远高于接口改动的成本**。

### 常见误区与考点
- ❌ **只算接口改动**。提示词里的模型特化补丁往往才是迁移的主要工作量，而且它们不报错、只降质。
- ⚠️ **考点**：为什么说评估基线是协议选型的前提？——没有它，换协议/换模型的收益无法度量，决策只能靠印象。

### 技术要点
- 失败模式的价值在于**可预期**：它们反复出现在不同项目里，且有稳定的成因
- 这一支与「安全」不同：安全关注**被攻击**，失败模式关注**自己坏掉**
- 四种最常见的形态：死循环与目标漂移、幻觉级联、提示腐化、无评测迭代
- **它们的共同点是「看起来在工作」**——没有报错，所以最容易被放任

### 深入讲解

为什么要把失败模式单列一支？因为它们**不会以报错的形式出现**。服务崩了你会立刻知道，但 Agent 陷入目标漂移时，它每一轮都在正常调用工具、正常返回内容、正常消耗预算。等你发现时，代价已经付出了。

四种形态的成因各不相同：

| 形态 | 成因 | 早期信号 |
| --- | --- | --- |
| 死循环与目标漂移 | 缺少外部状态量判据；目标表述足够模糊以至于可以被替换 | 工具调用次数上升、外部状态长时间不变 |
| 幻觉级联 | 未校验的结论进入上下文成为前提 | 后续结论开始引用一个没有出处的数字或事实 |
| 提示腐化 | 每修一个 bug 加一条规则，职责不断扩散 | 提示词长度单调增长，没人能说清每条规则为什么在 |
| 无评测迭代 | 没有可重复的评测，改动只能靠感觉验证 | 「这次好像好一点」成为发布依据 |

把这四种放在一起看，会发现它们都在**同一个方向上累积**：系统随着修补而变得更复杂，但可验证性下降。所以最有效的对策不是针对某一种失败加防护，而是**保持系统可观测与可回滚**：有轨迹、有评测、有外部状态量。这也是为什么「评估与上线」这一支在整张地图里处于兜底位置——它是判断其他部分是否真的在变好的依据。

### 常见误区与考点
- ❌ **把失败模式当成「多试几次就能避开」的运气问题**。它们有稳定成因，因此可被系统性预防。
- ⚠️ **考点**：为什么说目标漂移比死循环更危险？——死循环至少会撞上步数上限，目标漂移能在预算内产出「完成」的错误结果。

<!-- node: canon_fail_loop -->
### 技术要点
- **目标漂移**是目标在无人察觉时被替换为更容易达成的版本：从「修好这个测试」滑到「让测试通过」
- 它最危险的地方在于**过程完全正常**：工具调用合法、输出合理、状态显示完成
- 有效的防线是**把目标写成可核验的判据**，而不是描述性文字
- 一旦发现漂移，改的应该是**校验方式**（谁来判定完成），而不是加一句「不要偏离目标」

### 深入讲解

先看漂移是怎么发生的。任务开始时目标是「修复这个测试失败」，这个表述里没有任何机制约束「修复」的含义。执行几轮后遇到困难——真实修复需要改动一个共享模块，风险大；而修改断言的风险小、见效快。模型在每一步都做局部最优选择，于是逐步走到了「让测试通过」。**每一步都不算错，合起来是错的**——这正是它难以察觉的原因。

有效防线是**把完成条件外化**。对比两种表述：

- 描述性的：「修复失败的测试」——无法判定实现方式是否合规。
- 可核验的：「`npm test` 全绿，且 `git diff` 中不包含任何 `test/` 目录下的改动」——第二句直接排除掉最典型的漂移路径。

可核验的判据通常由三部分组成：**通过条件**（测试全绿）、**禁止事项**（不许改测试）、**边界**（只允许修改哪些目录）。这三者都可以用工具检查，于是「是否漂移」从主观判断变成程序判定。

另一个实用手段是**把禁止事项写进审批规则**，而不只是写进提示词。例如对 `test/` 目录的写操作触发人工确认——这样即使模型试图漂移，也会在动作层面被拦下来。提示词负责引导，权限负责兜底，两者的可靠性不在一个量级。

### 代码实例

```js
// 把「完成」写成可核验的三段式判据，并让禁止事项走审批而非仅靠提示
const GOAL = {
  passCondition: () => run('npm test').exitCode === 0,
  forbidden: [
    { pattern: /^test\//, reason: '禁止修改测试来让测试通过' },
    { pattern: /\.skip\(|\.todo\(/, reason: '禁止跳过测试' },
  ],
  // 允许改动的范围，超出即视为漂移
  allowedPaths: [/^src\//, /^package\.json$/],
}

function checkGoalCompletion(diff) {
  const touched = diff.files.map(f => f.path)
  const violations = GOAL.forbidden.filter(rule =>
    touched.some(path => rule.pattern.test(path)))
  if (violations.length) {
    // 明确返回漂移判定与原因，而不是「任务失败」
    return { done: false, drift: true, reasons: violations.map(v => v.reason) }
  }
  const outOfScope = touched.filter(path => !GOAL.allowedPaths.some(p => p.test(path)))
  if (outOfScope.length) return { done: false, drift: true, reasons: [`改动了范围外的文件: ${outOfScope.join(', ')}`] }
  return { done: GOAL.passCondition() }
}
```

### 常见误区与考点
- ❌ **靠加一句「不要偏离目标」来防漂移**。漂移不需要「故意」，它只是局部最优的累积结果。
- ⚠️ **考点**：为什么「禁止事项」应该同时写进审批规则？——提示词影响的是模型的选择倾向，权限影响的是动作能否发生，后者不依赖模型的配合。

### 技术要点
- 级联的起点是**一个未被校验的结论进入上下文**，之后它会被当作既定前提使用
- 它的传播方式是**引用**：后续轮次不会重新验证，只会在此基础上推理
- 最难发现的形态是「**数字类幻觉**」：格式完美、量级合理、出处不存在
- 防线只有一条实质有效的：**事实进入上下文前必须校验**，事后再查要回滚一整串推导

### 深入讲解

把级联拆成三步，防线也就清楚了：

1. **产生**：模型给出一个事实性陈述（数字、版本号、接口行为）。
2. **落地**：这个陈述被写进上下文（写进了文件、进了对话历史、被存进记忆）。
3. **引用**：后续轮次把它当前提，推导出更多结论。

关键的观察是：**第 2 步是唯一的收敛点**。到了第 3 步，错误已经扩散，修正需要把所有基于它的推导都重做。而在第 1 步拦截成本很高——你无法枚举「哪些陈述可能是幻觉」。

所以工程上的做法是在第 2 步设卡。具体分三类处理：

- **可查询的事实**：不允许模型直接陈述，必须走工具取数（这条在「事实性与幻觉」里有详述）。
- **模型生成的分析结论**：允许落地，但必须**带标记**「以下为判断，非已验证事实」，让后续轮次知道它的可信度。
- **工具返回的数据**：本身就是事实来源，但仍需校验格式与范围，防止工具异常把脏数据写进上下文。

关于「数字类幻觉」值得单独提醒：模型给出的错误数字往往**量级合理、格式完美**，这比明显荒谬的数字更危险，因为它不会触发任何告警。判定它需要外部依据，而不是看它像不像真的。

### 代码实例

```js
// 上下文写入前的关卡：按来源决定「能否作为事实被后续轮次引用」
function admitFact(statement, origin) {
  switch (origin.type) {
    case 'tool_result':
      // 工具返回：校验结构，异常数据不进上下文
      if (!origin.validated) return { admitted: false, reason: '工具返回未通过结构校验' }
      return { admitted: true, text: statement, trust: 'fact', evidence: origin.evidence }
    case 'model_claim':
      // 模型陈述：一律标记为判断，后续轮次不得当作事实引用
      return { admitted: true, text: `[判断，未验证] ${statement}`, trust: 'claim' }
    case 'human':
      return { admitted: true, text: statement, trust: 'fact', evidence: 'user_input' }
  }
}

// 后续轮次引用时按 trust 过滤，避免在 claim 之上继续推导
function quotableFacts(context) {
  return context.filter(item => item.trust === 'fact')
}
```

### 常见误区与考点
- ❌ **事后审计发现错误数字再去替换**。替换一个数字无法撤销建立在它之上的推导。
- ⚠️ **考点**：为什么模型生成的「分析结论」要带标记而不是直接禁止？——禁止会让循环无法推进，标记则保留了推进能力同时限制其被当作事实引用。

<!-- node: canon_fail_bloat -->
### 技术要点
- 提示腐化的典型曲线是**每条规则都有理由，但没有人能说清全部理由**
- 成因是「**用规则修 bug**」：每遇到一个反例就加一条约束，规则数量单调增长
- 三个具体症状：规则互相冲突、规则覆盖的是个案而非类别、规则没有可验证的判定方式
- 治理手段是**定期合并与淘汰**：把个案规则抽象成类别，把无法验证的规则删掉

### 深入讲解

腐化的过程可以预测，所以可以提前识别：

| 阶段 | 表现 | 可观测信号 |
| --- | --- | --- |
| 健康 | 规则按类别组织，每条能说出它防的是什么 | 规则数与功能数大致成比例 |
| 早期腐化 | 开始出现「当输入包含 X 时不要做 Y」 | 出现具体字符串、具体例子的规则 |
| 中期 | 新规则与旧规则边界模糊，偶尔冲突 | 修改一处需检查是否与另一处矛盾 |
| 晚期 | 没人敢删任何一条；新人不理解为何如此 | 提示词长度单调增长，无人能解释全貌 |

对应的治理动作有三个：

**个案抽象成类别。**「不要用 `rm -rf /`」是个案；「破坏性文件操作一律需要确认」是类别。前者的边际收益随幻觉形式变化而衰减，后者覆盖一整类动作。

**能用工具检查的，就不要写进提示词。**如果一条规则可以被程序判定（例如「输出必须是合法 JSON」），那它应该由校验器强制，而不是由提示词请求。提示词的可靠性依赖模型配合，校验器的可靠性不依赖。这条原则能消掉相当一部分规则。

**定期淘汰。**对每条规则问一个问题：删掉它，评测集上会发生什么？如果答不出来，要么评测集缺这个用例，要么这条规则已经无用。这个动作应该有节奏地做，而不是等到「不敢改」的时候才做。

### 代码实例

```js
// 把规则结构化：每条必须能回答「防什么、怎么验证」，答不出来的就该淘汰
const RULES = [
  {
    id: 'no-destructive-fs',
    kind: 'category',              // category 优先于 case
    prevents: '破坏性文件操作导致不可恢复的损失',
    enforcedBy: 'approval',        // approval | validator | prompt —— 优先用前两者
    test: 'redteam:escape-workspace-write',
  },
  {
    id: 'json-output',
    kind: 'category',
    prevents: '输出无法被解析，浪费整轮',
    enforcedBy: 'validator',       // 能被程序判定的，交给校验器
  },
]

// 体检：找出「无强制手段」与「无法验证」的规则，它们是最该被清理的
function auditRules(rules) {
  return {
    promptOnly: rules.filter(r => r.enforcedBy === 'prompt').map(r => r.id),
    untestable: rules.filter(r => !r.test).map(r => r.id),
    caseLevel: rules.filter(r => r.kind === 'case').map(r => r.id),
  }
}
```

### 常见误区与考点
- ❌ **每条新规则都直接加进提示词**。这是腐化的唯一入口，且每次单看都很合理。
- ⚠️ **考点**：为什么「能被程序判定的规则不该写进提示词」？——提示词依赖模型配合，校验器不依赖；同一件事交给校验器，等于把它从「请求」变成「约束」。

<!-- node: canon_fail_eval_gap -->
### 技术要点
- 无评测迭代的表现不是「没有测试」，而是**改动的依据是印象**
- 它的核心问题在于**无法区分「变好了」与「换了个失败方式」**
- 最低成本的起点是**把失败案例固化成可重复执行的任务**，而不是构建完整的评测平台
- 评测集是**唯一能支撑「迁移/换模型」决策的资产**——没有它就只剩主观判断

### 深入讲解

先澄清一个误解：无评测迭代不等于不测试。很多团队有测试，但测试检验的是「接口是否返回 200」而不是「任务是否真的完成」。于是改动提示词之后，测试全绿，质量却可能下降——因为失败从「报错」变成了「静默出错」。

它的代价可以具体化。假设你在优化工具描述，改动后观察到几个失败案例消失了。这里有两种可能：

1. 整体质量提升，那些失败本来就会被修复。
2. 失败方式转移了——原来的案例消失了，但出现了新的、你看不到的失败。

**没有评测集就无法区分这两种情况**。而第二种在实践中相当常见。

最低成本的起步方式很朴素：**把真实失败案例收集起来，每条变成一个可重复执行的任务**。一条用例包含三部分：输入（用户请求与初始状态）、执行（允许调用的工具与环境）、判定（成功条件）。关键在于判定必须**可程序化**，否则用例无法自动回归。

一个实用的规模判断：**20 到 50 条覆盖主要任务类型的用例**，已经足够支撑「这次改动是变好还是变坏」的判断。追求覆盖率要到后期再做——先有价值再谈规模，这是这一支最常见的推进障碍：人们倾向于先建平台，结果平台建完了用例还是零。

最后，评测集的价值会外溢到其他板块：协议选型需要它比较迁移前后（见「协议选型与锁定成本」），失败归因需要它提供可重复的样本（见「失败归因方法」），灰度需要它作为发布门槛。**它是这张地图里少数几个被多处依赖的资产**。

### 代码实例

```js
// 一条用例 = 输入 + 环境 + 可程序化的判定；三部分缺一不可
const CASES = [
  {
    id: 'sql-readonly-guard',
    input: '帮我统计上周每天的活跃用户数',
    env: { dbUser: 'readonly', tables: ['events'] },
    // 判定落在外部可观测事实上：SQL 语句本身与执行结果
    assert: ({ sql, rows }) => ({
      pass: /^select/i.test(sql.trim()) && !/;\s*\w+/i.test(sql) && Array.isArray(rows),
      detail: { sql, rowCount: rows?.length },
    }),
  },
  {
    id: 'no-test-rewrite',
    input: '修好这个失败的测试',
    env: { repoFixture: 'failing-test-01' },
    assert: ({ diff, testExitCode }) => ({
      pass: testExitCode === 0 && diff.files.every(f => !f.path.startsWith('test/')),
    }),
  },
]

// 回归对比：看通过率与失败类型的分布变化，而不只看总数
function compare(baseline, current) {
  const gained = current.passed.filter(id => baseline.failed.includes(id))
  const lost = baseline.passed.filter(id => current.failed.includes(id))
  return { netDelta: gained.length - lost.length, gained, lost }
}
```

`compare` 里同时返回 `gained` 与 `lost` 是刻意的：只看净变化会掩盖「修好 3 个坏了 3 个」这种原地踏步。

### 常见误区与考点
- ❌ **先建评测平台再收用例**。平台没有用例支撑就只是空壳，而用例从第一周就能产生价值。
- ⚠️ **考点**：为什么「测试全绿」不等于质量提升？——测试检验的是接口与断言，而不是任务完成度；静默出错不会让测试变红。
